# Скорость Windows 0.27 через FreeTurn

Проверка началась вечером 18.11.2026 по Томску после жалобы на остановки видео YouTube. Пользователь сам переключал профиль. Тест измеряет три загрузки по 2 МиБ через HTTPS с [измерительного сервера Cloudflare](https://github.com/cloudflare/speedtest/blob/main/README.md). Для каждого прогона проверяются рабочий handshake, активный путь и число потоков. Замер включает ожидание первого байта. Это одна сессия каждого режима с обычным фоновым трафиком, а не тест самого видео YouTube.

| Режим | Скорость по попыткам, Мбит/с | Медиана | Время до «Подключено» |
| --- | --- | ---: | ---: |
| VK Relay/TCP, 16 потоков | 8,56 / 5,98 / 2,02 | 5,98 | 59 с |
| VK Relay/TCP, 12 потоков | 1,84 / 7,26 / 6,04 | 6,04 | 44 с |
| VK Relay/TCP, 4 потока | 2,99 / 1,88 / 2,97 | 2,97 | 16 с |
| VK Relay/UDP, 16 потоков | 2,54 / 4,48 / 4,43 | 4,43 | 61 с |
| Direct/DTLS, 4 потока | 11,58 / 14,70 / 8,39 | 11,58 | 2 с |

Обе сессии использовали системную маршрутизацию, WireGuard MTU 1280, DoH ядра и 4 потока на одну авторизацию. Все шесть ответов полностью получены с HTTP 200. За первую серию два процесса FreeTurn заняли в среднем около 29% одного логического ядра, за вторую — около 23%. Во время загрузок новых ошибок DNS и предупреждений ядра не зафиксировано. Четыре потока ускорили запуск в этом сравнении, а скорость загрузки снизилась. Результат одного сеанса на конфигурацию не устанавливает оптимальное число потоков.

19.11 по Томску пользователь сам подключил Direct. Подтверждены handshake, системная маршрутизация, тот же MTU 1280 и 4 из 4 потоков. Все три загрузки прошли с HTTP 200, счётчики трафика WireGuard выросли, внешний IPv4 совпал с тестовым VPS и сессия сохранялась. В этом сравнении Direct дал примерно 1,9× медианы Relay/TCP на 16 потоках и 3,9× при равных 4 потоках.

Затем пользователь сам подключил VK Relay/UDP. Аутентифицированный статус подтвердил фактический `vk` / `udp`, 16 потоков, 4 потока на учётные данные и MTU 1280. До статуса «Подключено» прошло 61 с, до готовности всех 16 потоков — около 74 с. Все три загрузки завершились с HTTP 200. Медиана 4,43 Мбит/с уступила 5,98 Мбит/с у TCP с 16 потоками, минимальная проба оказалась чуть выше (2,54 против 2,02). Одна серия на режим не устанавливает устойчивость. WireGuard handshake и внешний IPv4 тестового VPS подтвердились, та же UDP-сессия осталась подключённой. Остановки воспроизведения и запас буфера YouTube остаются непроверенными.

Контрольная проба с тестового VPS по SSH не состоялась. Скорость выхода VPS, нагрузка его службы и влияние конкретного TURN пути по этому замеру не разделены.

По решению пользователя основной режим проекта — VK Relay. Дальнейшее сравнение UDP/TCP и варианты оптимизации ядра зафиксированы в [исследовании скорости Relay](VK_RELAY_PERFORMANCE_RESEARCH.md).

**VK Relay/TCP, 12 потоков.** Пользователь вручную подключил профиль. Подтверждены 12 из 12 потоков, WireGuard MTU 1280, 4 потока на учётные данные и системная маршрутизация. Три загрузки по 2 МиБ завершились с HTTP 200. Медиана 6,04 Мбит/с практически совпала с 5,98 на 16 потоках. Соединение поднялось на 15 с быстрее, но просадка до 1,84 Мбит/с осталась. Все потоки стали готовы примерно через 51 с. Продолжает работать та же сессия, внешний IPv4 совпадает с тестовым VPS. Влияние на длительное воспроизведение и квота VPS в этой серии не измерялись.

Для ручного повторения из каталога проекта:

```powershell
dotnet build clients/windows/catalog-check/CatalogCheck.csproj -c Release -o .local-cache/windows-build/throughput-probe
./scripts/measure_windows_vpn_download.ps1 -StatusHelper .local-cache/windows-build/throughput-probe/CatalogCheck.dll -Path relay -Transport tcp -Streams 4
```

Помощник читает статус через штатный IPC с проверкой процесса службы. Сценарий выполняется по запросу, передаёт до 6 МиБ измерительных данных и прерывается при изменении соединения.
