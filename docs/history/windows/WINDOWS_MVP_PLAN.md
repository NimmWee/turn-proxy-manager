# Windows: первая рабочая версия

Поручение пользователя от 15.11.2026: сначала обычный Windows-клиент для существующего профиля FreeTurn, затем подписки и остальные функции. Работа без субагентов. Это отдельный клиент в `clients/windows/`; Linux control plane и `vendor/vps/` не меняются.

## Выбор основы

- `hackdiaz-dev/turn-proxy-android`: сохраняем формат `freeturn://` и ядро, но Android VpnService нельзя перенести на Windows без замены системного туннеля.
- `l1ch666/turn-proxy-android`, Desktop 2.7.0, commit `386f85f222704fdbcff79121b8e9c606ebc1be24`: просмотренный full-tunnel renderer поддерживает VLESS/Hysteria, нужного WireGuard renderer нет. Готовым Windows VPN для нашего профиля его не считаем.
- FreeTurn core v4.1.5, commit `f6b1f25767755d9bf34cbf78818b74c5062d7d0c`: использовать штатный `mobile.Start` как UDP transport и штатную CAPTCHA, без переписывания VK auth. `StartTunnel` на Windows не подходит: получение TUN из fd реализовано только Linux/Android.
- Системный WireGuard: официальный `golang.zx2c4.com/wireguard/windows v1.1.1` и подписанный WireGuardNT. Пользовательский интерфейс: WPF/.NET 8, WebView2 для штатной CAPTCHA.

## Граница прав и сеть

Обычный UI общается только с собственной службой через локальный named pipe: ACL для SYSTEM, администраторов и выбранного при установке SID; удалённые pipe-клиенты запрещены. Фиксированные операции import/status/connect/disconnect, ограниченные сообщения, никаких команд/путей от UI. Профиль шифруется DPAPI, каталог доступен SYSTEM/администраторам. UI не получает приватные ключи обратно.

Туннель работает отдельной SCM-службой с фиксированным именем `WireGuardTunnel$FTM`. В этом же процессе запускается FreeTurn transport: это необходимо проверить из-за process-specific исключения официального WireGuard kill switch. Внешние сокеты FreeTurn привязываются к исходному физическому интерфейсу через IP_UNICAST_IF/IPV6_UNICAST_IF; встроенное управление маршрутами FreeTurn отключено. Исключения для произвольных приложений не добавляются. Не трогаем чужие VPN-службы/адаптеры.

Статус SCM Running не равен работоспособному VPN. Отдельно показывать состояние transport, WireGuard handshake и подтверждение прохождения трафика. До реальной проверки маршрутов этот путь имеет статус экспериментального.

## Последовательность

1. Зафиксировать зависимости, воспроизводимую загрузку и лицензии; собрать совместный FreeTurn/WireGuard engine.
2. Строгий импорт freeturn v1: лимиты, запрет дубликатов JSON, hooks/команд, произвольного WG endpoint и неподдерживаемых режимов. Целевые проверки на утечку/порчу профиля.
3. DPAPI/ACL, фиксированный протокол IPC, службы и ограниченная установка/удаление собственных компонентов. Без автоподключения при установке.
4. Русский WPF UI: импорт, подключение/отключение, статус, штатная CAPTCHA через локальный WebView2. Без фиктивных настроек подписки/маршрутизации.
5. Сборка, офлайн-сценарий, проверки прав и безопасного отказа. Локальную установку/активацию VPN согласовать отдельно перед изменением маршрутов, как уже обещано пользователю.
6. После разрешения — отдельный Windows peer, реальный handshake/egress/DNS, отключение и восстановление сети. До этого Windows VPN E2E = NOT RUN. Не использовать одновременно ключи iPhone/Android.

Полное автотестовое покрытие не требуется. Проверки сосредоточены на ключах, IPC/ACL, отказе до сетевых изменений и удалении только собственных компонентов. Подписки, bootstrap, updater, полный набор routing presets и установщик с подписью — следующие итерации. Без сертификата собственные EXE явно обозначаются неподписанными.

## Состояние

Код первой версии и локальная сборка готовы; [фактические проверки](WINDOWS_MVP_CHECK.md) отделены от native E2E. Пользователь самостоятельно установил службы; затем в UI0.1.1 исправлена проверка SYSTEM broker, настоящий IPC/DPAPI импорт подтверждён. Драйвер/FTМ VPN не запускались; проверку подключения пользователь оставил себе. Отдельный Windows профиль применён на согласованном тестовом VPS и передан приватным файлом вне Git. Подписки/маршрутизация/прочие этапы по-прежнему впереди.
