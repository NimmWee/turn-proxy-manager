# Защита SSH: три ошибки → 365 дней

**Дата:** 10.11.2026. Пользователь разрешил настройку нового тестового VPS; рабочий сервер не затрагивается. Никакие пароли не сохраняются в репозитории.

Новое требование пользователя заменяет прежние 30 дней из baseline: 3 ошибки SSH за 10 минут, бан IP на 31536000 секунд (365 дней), без случайного/прогрессивного увеличения. Loopback исключён; внешний IP администратора постоянного исключения не получает.

1. Проверить ОС, ресурсы, SSH-порты и существующие службы по сохранённому SSH-каналу. **Выполнено:** чистая Ubuntu 24.04, 1 CPU, 961 MiB RAM, SSH 22, VPN/Fail2ban отсутствуют.
2. Добавить тесты и `ftm/ssh_protection.py`: строгая валидация SSH-портов; конфигурация jail и хранения bans; backup прежних конфигов, atomic write, `fail2ban-client -t`, start/reload, проверка эффективных значений и rollback при ошибке. SSH не перезапускать.
3. Добавить отдельную root-only команду `python -m ftm secure-ssh --apply`. Она не делает доступным основной install/apply Manager. Пакеты ставятся отдельно из Ubuntu apt: fail2ban, python3-systemd, nftables.
4. Развернуть протестированный код на тестовом VPS. Сохранить конфиги до изменения, включить Fail2ban; существующий SSH-канал сохранить до проверки нового входа.
5. Проверить три synthetic failures для TEST-NET IP: после двух ban отсутствует, после третьей — есть; nftables содержит адрес; reload/restart восстанавливает ban из SQLite; удалить только тестовый ban. Фильтр sshd проверить отдельно на synthetic OpenSSH log lines.
6. Выполнить новый SSH-вход, сохранить очищенный отчёт и команды разблокировки в документации. Секреты и IP SSH-клиента не публиковать.

Особенность baseline: его `configure_fail2ban()` ожидает 30 дней. Нельзя после новой политики напрямую вызывать старую процедуру настройки и считать её успешной. Будущий оркестратор установки должен использовать новый модуль защиты вместо старого hook; файлы `vendor/vps/` остаются неизменными.
