## Выбор и границы

Рассмотрены live apply полученного профиля (опасен разрывом/нуждается в Connection Manager), фоновое автоматическое обновление (добавляет scheduler/identity/revoke scope) и explicit refresh + staging (выбрано). По кнопке «Проверить обновление» при подтверждённом VPN GET subscription через существующий internal HTTPS transport.200 валидируется до atomic DPAPI записи Pending;202/304 не меняют профиль; ошибки оставляют текущую конфигурацию/ключ. Никаких новых DNS/маршрутов/WFP или apply IPC. User token/enrollment, periodic refresh, seamless auto failover и подтверждённый трафиком LKG остаются следующим блоком.

Native Go builder принимает manifest + текущий share + ожидаемые device/public key/origin + ETag + revision high-water. Strict exact fields/duplicates/size/types, derived WG public key, device/origin/TLS/internal/API binding, canonical SHA256 ETag как Python ensure_ascii=False/sort_keys/separators. Клиентский private key берётся только из текущего локального WG, никогда из ответа. Baseline10.77.43/24, public IPv4 DNS, WireGuard/rtpopus3 и фактические лимиты Windows; несовместимые v1 возможности отвергать, не усекать. Другие schemas/unknowns/понижение revision/другой device/key/origin/неверный ETag — отказ без изменения каталогов. Same revision + новый ETag допустим: server transport settings имеют общий ETag, но device revision не обязана меняться.

На стороне C# отдельные ManagedConfig(Pending/Applied) и PreviousShare/PreviousConfig, SeenRevision. Пока Pending не применён, рабочий Share остаётся byte-identical. Явное «Использовать при следующем подключении» повторно проверяет builder, сохраняет Previous и меняет только локальный Share; открытый VPN остаётся нетронутым. Явный локальный rollback возвращает Previous, high-water не понижает. Возврат не обещает, что сервер продолжает принимать старый PSK/CID/адрес. При401/403 сохранить AccessDenied без удаления ключей; блокировать последующие Connect/apply/rollback до успешного authenticated refresh либо новой выдачи. Активная служба не останавливается вслепую: текущий IPC не сообщает matching profile identity, server peer revoke остаётся серверной обязанностью. Полный runtime revoke/LKG acceptance требует Connection Manager и отдельной приёмки.

304 допустим только для ранее проверенного Pending/Applied с тем же ETag; без cache это ошибка. Cached config перед conditional request повторно валидируется Go builder; malformed cache не превращается в trusted304. Responses/time/body/headers ограничены, redirects/proxy/cookies/HTTP3/fallback запрещены прежним транспортом. Token только Authorization, никаких query/body/private fields в диагностике. При несовпадении snapshot после await — отказ commit, не перезапись чужих изменений. Backup/merge сохраняют текущие credentials/candidates/high-water; обычные профили совместимы, managed metadata требует новой версии приложения.
