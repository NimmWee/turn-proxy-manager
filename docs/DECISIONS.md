# Принятые решения

## 001. Сохранить Vps отдельно и без изменений

`vendor/vps/` — точная копия commit из lock. Новый код находится в `ftm/`; общий импорт использует только валидатор и чистые функции старого модуля, не его CLI. При импорте не запускаются systemd, network-up, установка или генерация ключей.

Почему: исходная установка действительно проверяет ровно два устройства и кодирует их адреса. Переписывать её до baseline/E2E опасно. Изменения этапа 2 должны пройти отдельный путь миграции, не заменять baseline.

## 002. Первый установщик только анализирует

`install.sh` работает из локального checkout и вызывает `python3 -m ftm install`. Он не является удалённым bootstrap для `curl | bash` и не скачивает пакеты. Необязательный `--manager` поддержан для skeleton-совместимости; он не меняет режим безопасности.

`--dry-run` показывает план; без него код возврата 3, никакой установки. Мастер не требует обязательного `--domain`. Пока доступны только выбор режима, адреса, TLS/access policy и подтверждение просмотра. Пароли, DNS/TLS validation, настоящие apply/rollback и выпуск подписки будут реализованы позже, а не имитируются.

`preflight` читает ОС, root/systemd, CPU/RAM/диск, привязанные TCP/UDP-порты и наличие инструментов. Он не подтверждает DNS, firewall, доступность из интернета или health служб. Поэтому `installation_ready` всегда false. Root требуется будущему apply, но для запуска dry-run/inspect не нужен.

## 003. Конфигурация — строгий JSON

`--config FILE` читает данные, а не shell source/eval. Поля и типы проверяются, неизвестные/повторяющиеся поля запрещены, размер ограничен 64 KiB. POSIX: только обычный файл 0600, владелец root или текущий пользователь, без symlink. Состояние Vps ограничено 1 MiB.

Расширение файла не определяет формат: пример из ТЗ `/root/ftm-install.env` может содержать этот JSON. В документации используем `.json`, чтобы не вводить в заблуждение. Пароли и другие секреты не принимаются как параметры CLI.

На Windows POSIX-права не проверяются. На WSL/NTFS без metadata chmod может не сработать: полный тестовый прогон переносит код в временный каталог Linux и там проверяет 0600. Это не обход проверки на production.

## 004. Не подменять доверенный TLS обещанием

Публичный домен требует policy `domain`, публичный IP — `ip-trusted`; закрытый VPN/SSH-доступ — `private`. Валидация policy не выдаёт сертификат и не доказывает доверие. Публичный HTTP или отключение проверки сертификата не предусмотрены.

## 005. Сохранность миграции важнее изменения сетевого плана

Если обнаружено состояние Vps, fresh запрещён. migrate/repair требуют валидное состояние. План наследует существующие порты/subnet; явно конфликтующие параметры отклоняются. Секреты не включаются в результат. Endpoint VPN не заменяется адресом будущей веб-панели.

До реального apply обязательны зашифрованная копия вне VPS, проверка восстановления и rollback. WG keys/PSK, CID, VK link, obf key, старые профили, SSH/Fail2ban и чужие peers/rules/services должны сохраняться. Миграция на этапе 1 **не выполняется**.

## 006. Версии и доказательства

Все шесть upstream snapshots закреплены SHA. В baseline сохранены Go mod/sum; новых runtime Python-зависимостей пока нет. Android/Windows зависимости будут закреплены перед соответствующими этапами. Go/AAR/клиенты не пересобирались; arm64 только проверен по хешу.

Unit tests, subprocess CLI tests, реальный PTY-мастер, binary startup/CID smoke и настоящий VPN E2E — разные категории доказательств. Нельзя считать зелёный smoke доказательством подключения Android/iPhone через VK.

## 007. Порядок и работа

Локальные изменения выполняются без промежуточных разрешений; с 10.11.2026 — без субагентов по указанию пользователя. Развёртывание на действующий VPS не разрешено. GitHub remote настроен, push не выполняется без поручения.

Полный переход к этапу 2 зависит от приёмки этапа 1 на VPS/реальных устройствах. До этого выполняются все доступные задачи этапа 1 и фиксируются конкретные непройденные проверки.

Пользователь подтвердил наличие только рабочего VPS. Согласованного тестового deploy нет; fresh install/reinstall на нём не выполняется. Исходная серверная функциональность в этом шаге не меняется.

## 008. Предоставлен отдельный тестовый VPS; годовой бан SSH

После первоначального этапа пользователь предоставил отдельный тестовый VPS и разрешил установить Fail2ban. Это заменяет прежний блокер отсутствия тестового хоста, но не закрывает VPN E2E автоматически. Рабочий VPS не затрагивается.

Новое требование имеет приоритет над исходными 30 днями: maxretry 3, findtime 600, bantime 31536000, dbpurgeage 31622400. Реализована отдельная явная команда `secure-ssh --apply`, не включающая общий install/apply Manager. На тестовом VPS проверены фильтр, порог, nftables, сохранение и восстановление бана после перезапуска Fail2ban, идемпотентность и новый SSH-вход. [Отчёт](SSH_PROTECTION.md).
